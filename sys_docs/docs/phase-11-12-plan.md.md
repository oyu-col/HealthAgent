# Phase 11–12 的范围、步骤与验收边界

## 文件定位

这份计划在规范第22–29节基础上定义Domain Benchmark与优化闭环的工作目标。它承接已有Phase0–10实现，不要求重新搭建Agent或UI，也不将计划本身当作“已经验证”的证据。

Phase11目标是版本化20–30个案例、真实状态判分和完整可运行评测链；Phase12目标是先冻结基线，再根据真实失败修复，最后在相同协议下复测。源文件中的目标数与步骤是计划范围，当前实际29例及结果需结合交付文件与验收JSON阅读。

## 主要设计约束

- 每案例使用独立临时SQLite/checkpoint及合成身份，不触及现有私人data。
- 用户input、工具schema和真实observation可以给模型；expected_state、评分答案不得进入模型上下文。
- contract脚本与provider真实模型分开，工程路径通过不能替代自然语言规划/医学质量。
- 数据库状态、真实工具调用、SQL citation和持久Trace共同判分，模型声称成功不能自证。
- 保留失败、明确分母与未知值，不持久化凭据、URL、原始异常或真实健康资料。
- 任何案例/评分器/协议变化都要求重新建立可比基线，不能改答案后声称业务提高。

## 验收与现实限制

计划记录当时已有真实provider配置，但仅检查模式/必要项是否存在，未打印凭据。实际外部服务可能不可达；此时保留可运行入口和真实失败，不以fake替代。当前无Git元数据，用SHA-256标识源码和协议。

没有新增前端工作流需求，因此本阶段重点在评测、失败分析及可重复性，保持既有DeerFlow风格UI。实际阶段修改包括phase值同步，不代表重新设计UI。
