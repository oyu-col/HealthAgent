# Phase 11–12 实施与验收计划

日期：2026-10-11。依据规范第 22–29 节推进 Domain Benchmark 和 Baseline → Failure Analysis → Optimization → Benchmark Again。已有 Phase 0–10 能力继续复用。

## Phase 11 — Benchmark

- 建立 20–30 个版本化合成任务，覆盖单工具查询、写入、RAG、多工具、多 Agent、缺参、歧义、失败、超时、恢复、安全和循环。
- 独立的 case、runner、grader、report；评分读取实际数据库、工具 observation、citation 和持久 Trace，不因回答自称成功判分。
- 每个任务使用临时 SQLite/checkpoint、固定合成身份和显式环境；不触碰现有私人 data。只把用户输入与工具 schema/真实 observation 交给模型，不给它 expected_state 或评分答案。
- 分开运行离线契约模型与显式真实 provider。离线指标仅验证工程路径，模型选择/参数/语言理解质量不能由脚本化决策证明。
- 指标明确分母、未知值和适用范围，保留失败样本。输出不保存密钥、服务地址、真实用户资料或原始异常。

## Phase 12 — Evaluation & Optimization

- 先冻结案例/判分协议及当前源码指纹，实际运行 baseline。
- 从真实失败记录定位问题，先增加可复现回归测试，再实施范围明确的修复。
- 同案例、同评分器、同运行配置重新评测；额外重复运行观察波动。任何不可比较变化均在报告中标记，不以改答案制造提升。
- 输出前后差异、分类失败分析和未解决问题；工程基准提升与真实模型结果分别说明。
- 同步项目 README、阶段交付、架构和相关 sys_docs；既有历史验收不改写。

## 验证边界

真实模型已存在配置，本次只检查了模式和必要项是否存在，没有打印凭据。真实调用只使用合成数据和有界次数；若服务不可用，保留可运行入口与实际失败，不用 fake 冒充 live。当前没有 Git 元数据，使用源码 SHA-256 标识实验版本。前端没有新需求时保持既有交互，阶段工作重点在可重复评测闭环。
